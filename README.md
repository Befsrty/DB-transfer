# DB-transfer

DB-transfer переносит структуру хранилища данных SAP BW в Greenplum-совместимую СУБД (Arenadata DB, Greengage, Greenplum 6) и проверяет, что после переноса отчёты получают те же цифры.

На вход подаются CSV-выгрузки таблиц метаданных BW, сделанные транзакцией SE16. По ним приложение:

- строит модель хранилища: InfoObject, ADSO, DataSource, трансформации с правилами и рутинами, DTP;
- оценивает, какая часть объектов переносится автоматически, а какая требует ручной работы, и считает трудоёмкость по нормам;
- показывает схему потоков данных и путь любого поля (lineage) от источника до запроса и обратно;
- генерирует пакет SQL для целевой СУБД: схемы, таблицы справочников, DataSource и ADSO, функции активации и трансформаций;
- разворачивает пакет в базе, загружает тестовые данные, прогоняет их по потоку и сверяет результат с эталоном из BW.

Работать можно в веб-интерфейсе или из командной строки. В репозитории есть демо-набор: синтетическая выгрузка BW с потоком «Продажи» (плоский файл, два уровня ADSO, CompositeProvider, запрос), тестовые данные и эталоны.

Текущая версия — прототип 0.1. Требования к нему описаны в [docs/tz-prototype.md](docs/tz-prototype.md), результаты приёмочных испытаний — в [docs/acceptance.md](docs/acceptance.md).

## Требования

| Программа | Windows | Linux, macOS |
|---|---|---|
| Docker | [Docker Desktop](https://www.docker.com/products/docker-desktop/) с включённым WSL2 | Docker Engine и плагин Compose v2 (`docker compose version` должна работать) |
| uv | В PowerShell: `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 \| iex"` | `curl -LsSf https://astral.sh/uv/install.sh \| sh` |
| Git | [git-scm.com](https://git-scm.com/download/win) | `sudo apt install git` или аналог |

Python отдельно ставить не нужно: `uv sync` сам скачает Python 3.12.

Компьютеру нужно 16 ГБ оперативной памяти и 20–30 ГБ свободного места. Работа проверена на Windows 11 (x86-64, Docker Desktop с WSL2) и на Linux в CI. Запуск образа Greengage на Apple Silicon не проверялся.

## Установка

Linux и macOS:

```bash
git clone https://github.com/Befsrty/DB-transfer.git
cd DB-transfer
cp .env.example .env
docker compose up -d
uv sync
uv run dbtransfer db check
```

Windows (PowerShell):

```powershell
git clone https://github.com/Befsrty/DB-transfer.git
cd DB-transfer
Copy-Item .env.example .env
docker compose up -d
uv sync
uv run dbtransfer db check
```

Перед `docker compose up -d` Docker Desktop должен быть запущен. Первый запуск скачивает образ Greengage (около 1 ГБ) и инициализирует базу, на это уходит 1–3 минуты. Пока база не готова, `db check` сообщает, что подключиться не удалось; в этом случае нужно подождать и повторить команду. Когда всё готово, `db check` печатает версию Greengage и строку «Права на создание схем есть».

Параметры подключения (порт, база, пользователь, пароль) задаются в `.env`. По умолчанию база слушает порт 15432, чтобы не конфликтовать с локально установленным PostgreSQL.

Проект не следует размещать в папке OneDrive: синхронизация мешает `uv` создавать окружение.

## Быстрый старт

Весь путь на демо-наборе выполняется одной командой:

```
uv run dbtransfer run-demo
```

Сценарий импортирует демо-выгрузки, строит отчёт о сложности, генерирует SQL, разворачивает его с пересозданием схем `dbt_*`, загружает справочники и две загрузки продаж, прогоняет их по потоку `ZSALES_FF → ZSD_A01 → ZSD_A02`, сверяет оба ADSO с эталонами и печатает итог:

```
Итог
  Объектов уровня 1        26 из 33 (79%)
  Ручная работа по нормам  28 ч
  Строк SQL                818
  Объектов БД              38
  Загрузок                 ZSALES_FF_load1.csv: 503 строк, ZSALES_FF_load2.csv: 100 строк
  Сверка ZSD_A01           совпало 550 из 550
  Сверка ZSD_A02           совпало 142 из 142
  Время                    10.3 с
Демо прошло: цифры совпали с эталоном
```

Результаты лежат в `demo/out/`: отчёты `import_check.xlsx` и `complexity.xlsx`, пакет `sql/`, журнал развёртывания `deploy_<номер>_<время>.csv`, протоколы сверки `reconcile_*.xlsx`. Те же журналы записываются в схему `dbt_meta` базы. На обычном PostgreSQL строк SQL меньше, чем на Greengage, потому что в DDL нет параметров хранения и распределения.

## Веб-интерфейс

На Windows интерфейс запускается двойным щелчком по `start-ui.bat` в папке проекта. Файл при необходимости запускает Docker Desktop, поднимает базу, дожидается её готовности и открывает интерфейс в браузере. Окно консоли нужно держать открытым всё время работы: при его закрытии интерфейс останавливается. Ярлык на рабочем столе создаёт `make-shortcut.bat`; его достаточно запустить один раз, а после переноса папки проекта — повторно.

На любой системе интерфейс запускается из терминала:

```
uv run dbtransfer ui
```

Интерфейс открывается по адресу `http://localhost:8501`. Другой порт задаётся параметром `--port`, другой проект — `-p`, другой файл подключения — `--env-file`. Остановка — Ctrl+C в терминале.

| Вкладка | Назначение |
|---|---|
| Импорт | Список таблиц BW для выгрузки, импорт папки с CSV, найденные проблемы по файлам, Excel-отчёт о проверке |
| Схема | Схема потоков с фильтрами по типам и слоям; цвет рамки узла — уровень автоматизации, красное ребро — трансформация с рутиной. В списке «Карточка» выбирается объект или трансформация: поля, таблицы в целевой базе, правила, код рутины. Кнопки «Откуда пришло» и «Куда идёт» показывают lineage поля и подсвечивают путь на схеме |
| Сложность | Сводка по типам и уровням, список объектов с причинами, рутины ABAP, Excel-отчёт |
| SQL | Пакет SQL по файлам или по объекту, скачивание архивом |
| Развёртывание | План, развёртывание (пересоздание — с подтверждением), загрузка CSV из папки данных или выбранного файла, прогон по номеру загрузки, журнал загрузок, кнопка «Запустить демо целиком» |
| Сверка | Выбор объекта, эталона и допуска; итог по статусам, суммы по показателям, расхождения, протокол Excel |

Вкладки «Импорт», «Схема», «Сложность» и «SQL» работают без базы. Состояние подключения показывается в боковой панели.

## Командная строка

Команды работают с проектом — папкой, в которой лежит `project.yaml`. По умолчанию это текущая папка, а в корне репозитория — демо-проект `demo/`. Другой проект задаётся параметром `-p <папка>`.

```
uv run dbtransfer tables                          # какие таблицы BW выгрузить и как (подробно: docs/bw-export.md)
uv run dbtransfer import                          # импорт demo/bw_export -> demo/model.json, demo/out/import_check.xlsx
uv run dbtransfer report                          # отчёт о сложности -> demo/out/complexity.xlsx
uv run dbtransfer scope --from ZSD_A02            # состав переноса: поток от ZSD_A02 вниз до источников
uv run dbtransfer lineage ZSD_A02.0NETVAL_INV     # откуда пришло поле
uv run dbtransfer lineage ZSALES_FF.NETVAL --up   # куда идёт поле
uv run dbtransfer generate                        # пакет SQL -> demo/out/sql
uv run dbtransfer generate --scope                # только состав переноса из project.yaml
uv run dbtransfer deploy                          # развернуть пакет в базе (журнал dbt_meta.deploy_log)
uv run dbtransfer deploy --recreate               # пересоздать таблицы, тестовые данные удалятся
uv run dbtransfer load 0MATERIAL demo/data/md_0MATERIAL_attr.csv   # справочник
uv run dbtransfer load ZSALES_FF demo/data/ZSALES_FF_load1.csv     # плоский файл, выводит load_id
uv run dbtransfer run 5                           # прогон загрузки 5 по составу переноса
uv run dbtransfer rollback 5                      # откат ещё не прогнанной загрузки
uv run dbtransfer reconcile ZSD_A02 demo/data/etalon_ZSD_A02.csv   # сверка, протокол в out/
uv run dbtransfer init C:\work\my-bw              # новый проект для своей выгрузки
uv run dbtransfer ui                              # веб-интерфейс на http://localhost:8501
```

Команды, которые обращаются к базе, берут подключение из `.env` (другой файл — `--env-file`). Диалект SQL выбирается по серверу: Greengage/Greenplum или обычный PostgreSQL.

### Lineage

Пример на демо-наборе:

```
ZSD_A02.0NETVAL_INV [dbt_mart.zsd_a02_active.netval_inv]
└─ ← прямое присвоение (ZSD_A01 → ZSD_A02) ZSD_A01.0NETVAL_INV [dbt_dwh.zsd_a01_active.netval_inv]
   ├─ ← формула NETVAL - DISCOUNT (ZSALES_FF → ZSD_A01) ZSALES_FF.NETVAL [dbt_stg.zsales_ff.netval]
   └─ ← формула NETVAL - DISCOUNT (ZSALES_FF → ZSD_A01) ZSALES_FF.DISCOUNT [dbt_stg.zsales_ff.discount]
```

В квадратных скобках указано, где поле лежит в целевой базе (схема.таблица.колонка). Формула ветвит путь по своим полям, чтение атрибута — в поле-ключ и справочник, константа завершает путь, рутина обрывает его. Шаг через трансформацию с конечной рутиной помечается «возможно изменено рутиной».

### Пакет SQL

`generate` пишет в `out/sql/` файлы в порядке развёртывания:

| Файл | Содержимое |
|---|---|
| `010_schemas.sql` | Схемы `dbt_stg`, `dbt_md`, `dbt_dwh`, `dbt_mart`, `dbt_meta` |
| `020_meta.sql` | Журнал загрузок, журнал развёртываний, результаты сверок, последовательности номеров |
| `030_md.sql` | Атрибуты и тексты признаков (`dbt_md.material_attr`, `dbt_md.material_text`, …) |
| `040_datasources.sql` | Входные таблицы DataSource с колонками `load_id`, `record_no` |
| `050_adso.sql` | Таблицы ADSO: входящая, активные данные, журнал изменений в зависимости от вида ADSO |
| `060_activation.sql` | Функции активации: `dbt_dwh.activate_zsd_a01(load_id)` и т. д. |
| `070_transformations.sql` | Функции трансформаций: `dbt_dwh.tr_zsales_ff__zsd_a01(load_id)` и т. д. |
| `deploy_all.sql` | Всё одним файлом для `psql` (первая строка — команда `psql`, DBeaver её не понимает) |
| `drop_all.sql` | Удаление схем вместе с данными |

Пакет можно развернуть и без приложения: в DBeaver выполнить по очереди файлы `010`…`070` как скрипты (Alt+X) или, если установлен клиент PostgreSQL, выполнить `psql -h localhost -p 15432 -U gpadmin -d demo -f demo/out/sql/deploy_all.sql`. Повторный запуск безопасен: таблицы создаются с `IF NOT EXISTS`, функции заменяются. Генерация детерминирована: два запуска на одной модели дают одинаковые файлы.

Трансформация с ABAP-рутиной или правилом, которое приложение не переводит (в демо — `ZSD_A01 → ZSD_A03`), создаётся как заготовка: в комментарии лежат черновик SQL и код рутины, а сама функция завершается ошибкой «требует ручной доработки». Параметр `--dialect postgres` убирает из SQL особенности Greenplum (хранение и распределение) для обычного PostgreSQL.

### Развёртывание, загрузка, прогон, сверка

- `deploy` создаёт схемы, таблицы и функции одной транзакцией, пишет результат по каждому объекту в `dbt_meta.deploy_log` и копию в `out/deploy_<номер>_<время>.csv`. Если модель или правила изменились с прошлого развёртывания, а таблицы уже существуют, `deploy` останавливается и требует `--recreate`, иначе таблицы остались бы в старом виде. `--recreate` удаляет схемы с данными и журнал загрузок; журналы развёртываний и сверок сохраняются.
- `load` грузит CSV в два шага: файл копируется в сырую таблицу `dbt_stg.<имя>_raw` (все колонки текстовые), затем запрос проверяет значения и переносит строки в рабочую таблицу. Поддерживаются десятичная запятая, даты `ГГГГММДД` и `ДД.ММ.ГГГГ`, пустая дата и `00000000`. Если хотя бы одно значение не приводится к типу, загрузка отменяется целиком и выводятся первые 20 ошибок с номером строки, полем и значением. Повторная загрузка того же файла требует `--force`.
- `run` прогоняет загрузку DataSource по составу переноса (`scope_from` в `project.yaml`): трансформации и активации выполняются одной транзакцией. Если в потоке есть заготовка с рутиной, прогон не начинается. Загрузки прогоняются строго по возрастанию номера, повторный прогон отклоняется.
- `reconcile` сверяет активные данные ADSO с эталоном по ключу и каждому показателю (допуск 0,01) со статусами «совпало», «расхождение», «нет в ADB», «нет в эталоне». Протокол сохраняется в Excel (`out/reconcile_<объект>_<время>.xlsx`) и в `dbt_meta.reconcile_result`. Если на верхнем слое есть расхождения, а рядом лежит эталон нижнего слоя (`etalon_ZSD_A01.csv`), сверяется и он.

Колонки эталона называются по InfoObject. Другое соответствие задаётся в `reconcile.yaml` проекта:

```yaml
ZSD_A02:
  columns: {Клиент: 0SOLD_TO, Месяц: 0CALMONTH}
  tolerance: 0.01
```

## Работа со своей выгрузкой

Демо-проект `demo/` изменять не следует: на нём построены тесты. Для своей выгрузки создаётся отдельный проект:

```
uv run dbtransfer init C:\work\my-bw
```

В папке появятся `project.yaml` и подпапки `bw_export` и `data`. Префикс схем в базе берётся из имени папки (`my_bw_stg`, `my_bw_dwh`, …), чтобы не пересекаться с демо-схемами `dbt_*`; при необходимости его можно поменять в `project.yaml`.

Пользователю необходимо разложить файлы так:

| Что | Куда | Имена файлов |
|---|---|---|
| Метаданные BW (структура хранилища), 21 таблица SE16 | `bw_export/` | По имени таблицы: `RSDIOBJ.csv`, `RSTRAN.csv`, … Список — `dbtransfer tables`, инструкция — [docs/bw-export.md](docs/bw-export.md) |
| Справочники (для прогона данных) | `data/` | `md_<признак>_attr.csv`, `md_<признак>_text.csv`, например `md_0MATERIAL_attr.csv` |
| Загрузки DataSource | `data/` | `<DataSource>_load<N>.csv`, например `ZSALES_FF_load1.csv` |
| Эталоны из BW для сверки | `data/` | `etalon_<ADSO>.csv`, например `etalon_ZSD_A02.csv` |

Метаданные нужны всегда, папка `data` — только для проверки переноса на данных. Первая строка файла данных содержит имена колонок: в загрузке это поля DataSource (`DOC_NUMBER`, `NETVAL`), в справочнике — признак и его атрибуты (`0MATERIAL;0MATL_GROUP`) или `LANGU;TXTSH;TXTLG` для текстов, в эталоне — InfoObject ADSO (`0SOLD_TO`, `0NETVAL_INV`). Разделитель — `;`. Образцы файлов лежат в `demo/data/`.

Дальнейшая работа такая же, как с демо: `uv run dbtransfer ui -p C:\work\my-bw` (или путь к папке в поле «Папка проекта» на боковой панели), затем «Импортировать», вкладки «Схема», «Сложность», «SQL» и при необходимости «Развёртывание» и «Сверка».

## Настройка правил

Правила переноса вынесены в YAML-файлы и меняются без изменения кода:

| Файл | Что задаёт |
|---|---|
| `dbtransfer/rules/bw_tables.yaml` | Состав таблиц BW, их колонки и ключи |
| `dbtransfer/rules/type_rules.yaml` | Перевод типов ABAP, хранение и ключи распределения. Одноимённый файл рядом с `project.yaml` переопределяет правила для проекта, раздел `overrides` — для отдельного объекта |
| `dbtransfer/rules/naming.yaml` | Имена схем и таблиц в целевой базе |
| `dbtransfer/rules/effort_norms.yaml` | Нормы трудоёмкости ручной работы |

Устройство приложения и порядок добавления нового источника или целевой СУБД описаны в [docs/architecture.md](docs/architecture.md).

## Ограничения

- Состав колонок таблиц BW собран по документации BW/4HANA, а не по настоящей выгрузке. Такие места помечены `hypothesis: true` в `dbtransfer/rules/bw_tables.yaml` и могут потребовать правки под реальную систему.
- ABAP-рутины не переводятся: генерируется заготовка, прогон через неё блокируется.
- Выгрузка SE16 должна содержать технические имена колонок (как описано в [docs/bw-export.md](docs/bw-export.md)); текстовые заголовки вроде «Имя таблицы» не распознаются.
- Генератора синтетических метаданных большого объёма для проверки производительности нет.
- Схема потоков статична: объект выбирается в списке «Карточка», клик по узлу ничего не делает.

## Тесты

```bash
uv run pytest          # модульные тесты, база не нужна
uv run pytest -m db    # интеграционные тесты с запущенной базой
```

Интеграционные тесты разворачивают сгенерированный SQL в отдельных схемах `dbtest_*` (демо-схемы `dbt_*` не затрагиваются) и прогоняют через функции пример, посчитанный вручную (приложение Д ТЗ): активные данные `ZSD_A01`, журнал изменений и `ZSD_A02` должны совпасть с `demo/data/micro/` строка в строку.

Тесты генерации сравнивают SQL с эталонными файлами в `tests/golden/sql/`. Если SQL изменился намеренно, эталоны обновляются командой `UPDATE_GOLDEN=1 uv run pytest tests/unit/test_generator.py` (в PowerShell: `$env:UPDATE_GOLDEN=1; uv run pytest tests/unit/test_generator.py; Remove-Item Env:UPDATE_GOLDEN`), после чего разницу нужно просмотреть в `git diff`.

CI в GitHub Actions на каждый pull request запускает модульные тесты, ruff, проверку покрытия и интеграционные тесты на Greengage 6.32.

## Подключение из DBeaver

Тип подключения PostgreSQL (или Greenplum), хост `localhost`, порт из `.env` (по умолчанию 15432), база `demo`, пользователь `gpadmin`, пароль из `.env` (по умолчанию `student`).

## Управление базой

```bash
docker compose ps          # состояние
docker compose logs -f     # журнал
docker compose down        # остановить, данные сохранятся
docker compose down -v     # остановить и удалить данные
```

## Частые проблемы

| Симптом | Решение |
|---|---|
| В `docker compose logs` бесконечно повторяется `getaddrinfo ...: Temporary failure in name resolution` | База создана контейнером с другим именем хоста (старая версия `docker-compose.yml`). Базу нужно пересоздать: `docker compose down -v`, затем `docker compose up -d` (тестовые данные удалятся) |
| `port is already allocated` при `docker compose up` | Порт из `.env` занят. Нужно указать другой свободный `DBT_DB_PORT` (например, 25432) и повторить `docker compose up -d` |
| `db check`: ошибка про пароль `gpadmin` или нечитаемые символы вместо текста | На порт отвечает не Greengage, а другой PostgreSQL (так бывает, если в `.env` указан 5432). Проверить порт можно командой `netstat -ano \| findstr <порт>` в Windows или `ss -ltnp \| grep <порт>` в Linux. Нужно указать свободный `DBT_DB_PORT`, выполнить `docker compose up -d` и снова `db check` |
| `db check`: Connection refused | Контейнер не запущен или ещё инициализируется. Состояние — `docker compose ps`, журнал — `docker compose logs -f` |
| `db check`: password authentication failed | Пароль в `.env` изменён после первого запуска. Пароль задаётся при создании базы: нужно вернуть прежний или пересоздать базу командой `docker compose down -v` (данные удалятся) |
| Docker Desktop на Windows не запускается | Нужно включить WSL2: в PowerShell от имени администратора выполнить `wsl --install` и перезагрузить компьютер |
| `uv` не находится после установки | Нужно открыть новое окно терминала, чтобы обновился PATH |
| `uv sync`: «Отказано в доступе» или os error 396 | Проект лежит в папке OneDrive. Его нужно перенести в обычную папку, например `C:\projects\db-transfer`, и задать `$env:UV_LINK_MODE = "copy"` |
| `uv sync`: os error 32 при обновлении | Файл занят запущенным интерфейсом. Нужно закрыть окно `start-ui.bat` или остановить `dbtransfer ui` и повторить `uv sync` |
| `dbtransfer ui`: порт 8501 занят | `uv run dbtransfer ui --port 8502` |
| Справка команд нечитаема в Git Bash | Использовать PowerShell или cmd либо задать `PYTHONUTF8=1` |
| В интерфейсе не видно изменений после `import` в терминале | Обновить страницу (F5): интерфейс перечитывает `model.json` по времени изменения файла |

## Демо-набор

Демо-набор синтетический: состав полей таблиц собран по документации BW/4HANA. Файлы создаются скриптами и хранятся в репозитории; тесты проверяют, что они совпадают с выводом скриптов.

```bash
uv run python demo/tools/make_bw_export.py   # метаданные BW -> demo/bw_export
uv run python demo/tools/make_demo_data.py   # данные и эталоны -> demo/data
```

Эталоны считаются на pandas независимо от SQL приложения: перезапись в standard ADSO с журналом изменений (пара X / ' ' со знаком минус у старых значений), суммирование в cumulative ADSO с сохранением нулевых строк. Сам расчёт проверен на примере, посчитанном вручную (`demo/data/micro/`).

В загрузке 1 даты в формате `ГГГГММДД`, есть пустая дата `00000000` и три повтора ключа (побеждает последняя запись). Загрузка 2 содержит по 10 корректировок каждого вида (сумма, месяц, клиент, валюта, повтор без изменений) и 50 новых позиций; вид каждой записан в `demo/data/load2_cases.csv`. Даты в загрузке 2 в формате `ДД.ММ.ГГГГ`, пустая дата — пустая строка. Суммы везде с десятичной запятой.

## Структура репозитория

```
dbtransfer/          пакет приложения
  rules/             bw_tables.yaml, naming.yaml, effort_norms.yaml, type_rules.yaml
  model/             модель метаданных (pydantic), сохраняется в model.json
  importers/         импорт CSV-выгрузок SE16
  analysis/          граф и состав переноса, уровни и трудоёмкость, Excel-отчёты, lineage
  generator/         генерация SQL: типы, формулы, таблицы, активация, трансформации, шаблоны Jinja2
  deploy.py          развёртывание пакета и журнал deploy_log
  runtime.py         загрузка CSV, прогон, откат
  reconcile.py       сверка с эталоном и протокол
  scenario.py        сквозной сценарий run-demo
  project.py         проект: project.yaml, model.json, out/
  config.py          правила и подключение из .env
  db.py              подключение к базе
  cli.py             команды dbtransfer
  ui/                веб-интерфейс Streamlit: app.py, схема потоков (schema.py), карточки (cards.py)
demo/
  bw_export/         синтетические CSV метаданных BW
  data/              справочники, загрузки, эталоны
  tools/             генераторы демо-набора
  project.yaml       демо-проект
tests/
  unit/              без базы
  golden/sql/        эталонный пакет SQL демо-проекта
  integration/       с Greengage (pytest -m db)
docs/                ТЗ, выгрузка SE16, сценарий демонстрации, архитектура, протокол приёмки
start-ui.bat         запуск базы и интерфейса двойным щелчком (Windows)
make-shortcut.bat    ярлык DB-transfer на рабочий стол (Windows)
docker-compose.yml   база Greengage
.env.example         параметры подключения (скопировать в .env)
```
