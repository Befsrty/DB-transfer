# Импорт из Oracle и MS SQL Server

Кроме выгрузок SAP BW, модель можно построить по словарю реляционной СУБД: Oracle (`ALL_*`) или MS SQL Server (`INFORMATION_SCHEMA` и `sys.*`). Дальше всё работает как для BW: отчёт о сложности, пакет SQL для Greengage/Arenadata DB, развёртывание, загрузка CSV с данными и сверка.

По умолчанию каждая таблица переносится 1:1: одна таблица с исходным именем и секциями, без входящей таблицы, активации и журнала изменений. Ключ `--target adso` включает прежний режим, в котором таблица становится потоком DataSource → ADSO, как объект BW.

## Как получить словарь

**Выгрузка в CSV.** Запросы печатает команда

```
uv run dbtransfer tables --source oracle      # или --source mssql
```

Каждый запрос выполняется в SQL Developer, DBeaver или SSMS, результат сохраняется в CSV с заголовком под именем из комментария (`ALL_TAB_COLUMNS.csv`, `COLUMNS.csv`, …), все файлы в одну папку. Обязательны два файла: `ALL_TABLES` и `ALL_TAB_COLUMNS` для Oracle, `TABLES` и `COLUMNS` для MS SQL Server. Без остальных импорт пройдёт, но не будет ключей, комментариев и отчёта о представлениях и коде. Кодировка (UTF-8 или Windows-1251) и разделитель (`,` `;` или табуляция) определяются автоматически, как у выгрузок SE16.

```
uv run dbtransfer init C:\work\my-oracle
uv run dbtransfer import C:\work\my-oracle\bw_export --source oracle -p C:\work\my-oracle
uv run dbtransfer import <папка> --source oracle --schemas HR,SALES   # только эти схемы
uv run dbtransfer import <папка> --source oracle --target adso        # поток DataSource → ADSO, как в BW
```

**Подключение к базе.** Нужен драйвер: `uv sync --extra oracle` (python-oracledb в тонком режиме, Oracle Client не нужен) или `uv sync --extra mssql` (pymssql). Пароль берётся из переменной `DBT_SRC_PASSWORD`, список схем обязателен:

```
set DBT_SRC_PASSWORD=...
uv run dbtransfer import --source oracle --url oracle://dwh_reader@ora-host:1521/DWH --schemas DWH,STG
uv run dbtransfer import --source mssql  --url mssql://reader@sql-host:1433/Shop --schemas dbo,sales
```

Выполняются те же запросы, что печатает `dbtransfer tables`. Запросы читаются порциями по 5000 строк, словарь на 10 000 таблиц по 30 колонок импортируется примерно за 5 секунд и около 500 МБ памяти. В интерфейсе на вкладке «Импорт» источник и режим переноса выбираются переключателями, импорт идёт из папки.

## Во что превращаются объекты

Режим по умолчанию, `--target table`:

| В источнике | В модели | В целевой базе |
|---|---|---|
| Таблица `SALES.ORDERS` с первичным ключом | Таблица `SALES.ORDERS` | `<префикс>_sales.orders` с PRIMARY KEY, распределение по первой колонке ключа |
| Таблица без первичного ключа, но с уникальным | То же, ключом берётся первый по имени уникальный ключ | То же |
| Таблица без ключей | Таблица без ключа | Таблица append-optimized, загрузка только добавлением |
| Секционирование RANGE и LIST (Oracle), RANGE LEFT и RIGHT (MS SQL) | Секции с границами | Greenplum: `PARTITION BY RANGE/LIST` в CREATE TABLE; PostgreSQL: `PARTITION OF` |
| Интервальное секционирование Oracle | Существующие секции и секция по умолчанию | То же; новые секции выделяются из секции по умолчанию |
| HASH, секционирование по нескольким колонкам, подсекции | Сведение в отчёте о проверке импорта | Не переносится, распределение делает Greenplum |
| Колонки | Поля с типом модели; тип источника и комментарий — в комментарии поля | Типы по `type_rules.yaml` |
| Представление | Прочий объект «Представление»: уровень 1, если переводчик перевёл его полностью, иначе 2; упомянутые таблицы — в связях | Переведённое — `080_views.sql`, с TODO — `drafts_views.sql` ([translator.md](translator.md)) |
| Материализованное представление | Прочий объект «Представление», уровень 2 | Не генерируется |
| Процедура, функция, пакет, триггер | Прочий объект «Процедура, функция, триггер»: уровень 2 (черновик PL/pgSQL, остаток часов по TODO) или 3, если перевести нечего | Черновик в `drafts_routines.sql`; триггеры — TODO |
| Внешний ключ, отключённый ключ | Сведения в отчёте о проверке импорта | Не переносится |

Схема в целевой базе — `<префикс>_<схема источника>` (`naming.yaml`, `schemas.source`), имя таблицы — исходное в нижнем регистре (`tables.db_table`). Таблицы попадают в файл пакета `045_tables.sql`.

Загрузка данных: `dbtransfer load SALES.ORDERS <файл>.csv` (подходят и `SALES_ORDERS`, и просто `ORDERS`, если имя однозначно). Колонки файла называются как колонки таблицы источника, загрузка сразу пишет в таблицу, `run` не нужен. Строки с тем же ключом перезаписываются, повторы ключа внутри файла сводятся к последней строке. Сверка: `dbtransfer reconcile SALES.ORDERS etalon.csv` — по ключу таблицы и тем числовым колонкам, которые есть в эталоне.

Режим `--target adso`: таблица становится DataSource `SALES_ORDERS` и ADSO standard (без ключа — staging), между ними трансформация из прямых присвоений и дельта-DTP. В базе это `dbt_stg.sales_orders`, `_inbound`, `dbt_dwh.sales_orders_active` и `_changelog`; загрузка — `load`, затем `run`. Секционирование в этом режиме не переносится.

## Перевод типов

| Oracle | MS SQL Server | Тип модели | Greengage |
|---|---|---|---|
| VARCHAR2(n), NVARCHAR2(n) | varchar(n), nvarchar(n) | CHAR | varchar(n) |
| CHAR(n), NCHAR(n) | char(n), nchar(n) | FIXCHAR | char(n), с дополнением пробелами, как в источнике |
| CLOB, NCLOB, LONG, ROWID | varchar(max), nvarchar(max), text, ntext, xml | STRING | text |
| NUMBER(p) при p ≤ 4 / ≤ 9 / ≤ 18 (для NUMBER(p,−s) считается p+s) | smallint / int / bigint | INT2 / INT4 / INT8 | smallint / integer / bigint |
| — | tinyint, bit | INT1 | smallint |
| NUMBER(p,s), NUMBER(p) при p > 18, NUMBER(\*,0) | decimal(p,s), numeric(p,s), money, smallmoney | DEC | numeric(p,s) |
| NUMBER без точности, NUMBER(p,s) при s > p | — | NUMERIC | numeric |
| FLOAT, BINARY_FLOAT, BINARY_DOUBLE | float, real | FLTP | double precision |
| — | date | DATS | date |
| — | time | TIMS | time |
| DATE, TIMESTAMP(n) | datetime, datetime2, smalldatetime | TIMESTAMP | timestamp |
| TIMESTAMP WITH (LOCAL) TIME ZONE | datetimeoffset | TIMESTAMPTZ | timestamptz |
| RAW, LONG RAW, BLOB | binary, varbinary, image, rowversion | BINARY | bytea |
| — | uniqueidentifier | CHAR(36) | varchar(36) |
| прочие (XMLTYPE, SDO_GEOMETRY, INTERVAL, …) | прочие (sql_variant, geography, hierarchyid, …) | как в источнике | text, с предупреждением |

Нераспознанный тип можно задать в `type_rules.yaml` проекта: ключ — имя типа в верхнем регистре, например `SDO_GEOMETRY: "text"`.

Формат значений в CSV с данными: числа с точкой или запятой (для NUMERIC и FLTP допустима экспонента `1e3`), даты `ГГГГ-ММ-ДД` (а также `ГГГГММДД` и `ДД.ММ.ГГГГ`), время `ЧЧ:ММ:СС`, дата и время `ГГГГ-ММ-ДД ЧЧ:ММ:СС[.дробь][±ЧЧ:ММ]` (допустим `T` между датой и временем), двоичные данные — шестнадцатеричной строкой, можно с `0x`. Для Oracle перед выгрузкой данных стоит выполнить `ALTER SESSION SET NLS_DATE_FORMAT = 'YYYY-MM-DD HH24:MI:SS'` и `NLS_TIMESTAMP_FORMAT = 'YYYY-MM-DD HH24:MI:SS.FF'`, иначе даты придут в формате сессии и загрузка их отклонит.

### Что меняется при переносе типа

Для колонок из строк ⚠ справочника типов импорт пишет замечание с именами колонок: предупреждение, если значения меняются, и сведение, если нет.

| Тип источника | Что происходит | Вид замечания |
|---|---|---|
| Oracle TIMESTAMP(7–9), MS SQL datetime2(7), time(7), datetimeoffset(7) | Доли секунды округляются до микросекунд | Предупреждение |
| Oracle TIMESTAMP WITH TIME ZONE, MS SQL datetimeoffset | timestamptz хранит момент в UTC, исходный пояс или смещение теряется | Предупреждение |
| Oracle NUMBER(p,s) при s < 0 или s > p, NUMBER без точности | Округление при записи, которое делал Oracle, не выполняется | Сведение |
| Oracle ROWID, UROWID | Адрес строки переносится текстом, смысла в новой базе не имеет | Сведение |
| CHAR(n), NCHAR(n), char(n), nchar(n) | char(n): пробелы справа сохраняются, сравнение без них | Сведение |
| MS SQL datetime | Точность 1/300 секунды, значения переносятся как есть | Сведение |
| MS SQL uniqueidentifier | Текст из 36 знаков, порядок сортировки MS SQL не сохраняется | Сведение |
| MS SQL timestamp, rowversion | bytea, новая база значения не обновляет | Сведение |
| MS SQL char, varchar, text в однобайтовой collation (Cyrillic_General_*) | Одно замечание на базу: данные выгружать в UTF-8 или Windows-1251, загрузчик определит кодировку сам | Сведение |
| MS SQL collation *_CI_* у колонок ключа | Загрузка и сверка сравнивают ключ через lower() | Предупреждение |
| sql_variant, hierarchyid, geography, SDO_GEOMETRY и прочие | text | Предупреждение |

## Допущения

1. **Режим 1:1 по умолчанию.** Таблица переносится одной таблицей с исходным именем. Если перенос должен идти через слои, как в BW (журнал изменений, активация), используйте `--target adso`.
2. **Ключ и секции.** Greenplum и PostgreSQL требуют, чтобы первичный ключ секционированной таблицы включал колонки секционирования. Если в источнике это не так (типично для Oracle с локальными индексами), таблица секционируется, а PRIMARY KEY не создаётся; загрузка всё равно перезаписывает строки по ключу. Генератор пишет об этом предупреждение.
3. **Секционирование**: переносятся RANGE и LIST по одной колонке. MAXVALUE и DEFAULT становятся секцией по умолчанию. Границы RANGE в MS SQL: RANGE RIGHT — нижняя граница входит в секцию (как в Greenplum), RANGE LEFT — верхняя входит, генератор пишет `INCLUSIVE`. HASH не переносится: в Greenplum его заменяет распределение.
4. **Ключ**: первичный, иначе первый по имени уникальный. Порядок колонок в PRIMARY KEY и ключ распределения (первая колонка ключа) — по порядку колонок в таблице, а не в ограничении.
5. **DATE в Oracle → timestamp**, потому что DATE хранит время. Если в DWH там только даты, тип меняется в `type_rules.yaml` проекта.
6. **NUMBER(10) → bigint**: 10 знаков не помещаются в integer. Целые значения вида `12300.0` (так их отдают некоторые драйверы) загружаются в целые колонки.
7. **Регистр ключа MS SQL.** Для ключей с collation *_CI_* загрузка и сверка сравнивают значения через lower(). В Greengage сравнение остаётся регистрозависимым: запросы, которые соединяют такие таблицы, пишите через lower().
8. **Сверка** идёт по ключу и тем числовым колонкам, что есть в эталоне. Текстовые колонки вне ключа не сверяются.
9. **Внешние ключи, индексы, последовательности, синонимы, гранты и значения по умолчанию не переносятся.** Внешние ключи видны в отчёте о проверке импорта.
10. **Связи представлений с таблицами** найдены поиском имён таблиц в тексте представления — без разбора SQL, возможны лишние или пропущенные связи. Текст представлений и код процедур переводит `dbtransfer.translate` ([translator.md](translator.md)); для процедур нужен текст: `ALL_SOURCE` с колонками `LINE` и `TEXT` у Oracle и `DEFINITION` в `ROUTINES` у MS SQL Server (запросы — `dbtransfer tables --source …`).
11. **Трудоёмкость**: представление 2 ч + 1 ч на каждые 50 строк, процедура 4 ч + 2 ч на каждые 50 строк (`effort_norms.yaml`) — это оценка ручного переноса; после перевода в отчёте показан остаток (проверка перевода и TODO). Нормы ориентировочные.
12. **Режим ADSO**: колонки источника с именами `load_id`, `record_no`, `recordmode` конфликтуют со служебными колонками и дают ошибку импорта; имена длиннее 63 символов с суффиксом `_changelog` дают предупреждение.

## На чём проверено

- Модульные тесты на синтетических словарях в `tests/data/`, включая все строки ⚠ справочника типов (`tests/unit/test_type_caveats.py`) и словарь на 2000 таблиц (`test_dict_scale.py`; на 10 000 — `tests/data/make_big_dict.py`).
- Сквозной прогон «развёртывание → загрузка → повторная загрузка → сверка» на Greengage 6.32 и PostgreSQL 16 (`tests/integration/test_dict_db.py`): секционированные таблицы, регистронезависимый ключ, файл в Windows-1251, datetime2(7).
- Живые базы в Docker: импорт по подключению, развёртывание, выгрузка данных из источника, загрузка и сверка в Greengage и PostgreSQL:
  - Oracle Database XE 21c и 23ai Free;
  - SQL Server 2017 и 2019, а также 2019 в режиме совместимости 130 (уровень SQL Server 2016).
- **Не проверено**: Oracle 19c (образ в Docker только с учётной записью Oracle; XE 21 — ближайшая доступная версия, запросы к словарю те же), SQL Server 2016 на настоящем движке (образа для Linux нет), Oracle 11g/12c. Запросы используют только представления, доступные без привилегий DBA (`ALL_*`, `INFORMATION_SCHEMA`, `sys.*` с правом VIEW DEFINITION), и не используют функций новее SQL Server 2016.
