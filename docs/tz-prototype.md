# Коротко

Документ задаёт, что именно должен уметь прототип DB-transfer, из каких частей он состоит, на чём работает и как проверить, что он готов. По нему пишется код и по нему же проводится приёмка перед защитой.

Прототип берёт CSV-выгрузки таблиц метаданных SAP BW (синтетические, в формате транзакции SE16), строит из них модель хранилища, выдаёт отчёт о сложности в Excel, показывает схему потоков, генерирует SQL для Greengage (открытый форк Greenplum, близкий к Arenadata DB 6), разворачивает объекты в локальной базе в Docker, прогоняет тестовые данные через учебный поток «Продажи» и сверяет итог с эталоном.

Объём соответствует поставке 1А из ревью целиком и тонкому срезу поставки 1Б на одном потоке. Поставка 1В (редактирование модели, разбор SQL обратно в модель, развёртывание через ALTER, версии, откаты) в прототип не входит.

Документ составлен по мотивам ГОСТ 34.602-2020 и ГОСТ 19.201-78 в упрощённом виде: разделы сохранены, формальности (листы согласования, подписи) опущены.

**Изменения в версии 1.2** (по ревью review-tz-prototype.docx):

- Загрузка CSV идёт через сырую текстовую таблицу с приведением типов в SQL (ФП-7.1, ФП-7.2).
- Повторная активация загрузки запрещена, загрузки активируются строго по порядку, прогон выполняется одной транзакцией (4.1.3, ФП-7.3, ФП-7.6…7.8).
- Зафиксирована семантика активации: значения `recordmode`, дубли ключа в загрузке, нулевые строки, единый `load_id` по цепочке (раздел 4.3.5); уточнены режимы DTP.
- Демо-корректировки обязательно включают смену месяца, клиента и валюты (4.3.7); добавлен пример, посчитанный вручную (приложение Д, ПИ-18).
- Lineage полей: убрано противоречие про CompositeProvider, добавлены рутины трансформации и чтение атрибута, ядро перенесено в шаг 2 (ФП-4.6, раздел 5, ПИ-16).
- Цель 2.1 сформулирована через эталон, а не через «цифры BW».
- Уточнены ALPHA, развёртывание при изменённой модели, соответствие полей трансформаций, испытания ПИ-12…ПИ-14, поддержка Apple Silicon, словарь формул; добавлены метрики эффекта (ФП-3.6, ФП-3.7) и версия формата модели.

# 2. Назначение и цели прототипа

## 2.1. Назначение

Прототип доказывает на одном учебном потоке, что структуру хранилища SAP BW можно перенести в Greenplum-совместимую СУБД без ручного написания DDL, а цифры на верхнем слое после переноса совпадут с эталоном, рассчитанным независимо от генератора по семантике BW, описанной в этом ТЗ (раздел 4.3.5).

Реальной BW у проекта нет, поэтому совпадение с цифрами настоящей системы прототип не доказывает. Чтобы эталон не повторял возможное непонимание BW автором кода, семантика дополнительно проверена на примере, посчитанном вручную (приложение Д).

## 2.2. Цели

1. Автоматическая инвентаризация: по выгрузкам метаданных получить полный список объектов хранилища, связи между ними и оценку, что переводится автоматически, а что вручную (поставка 1А).
2. Перенос без ручного DDL: для объектов уровня 1 потока «Продажи» сгенерировать и развернуть таблицы, справочники, функции активации и трансформации (срез поставки 1Б).
3. Доказательство корректности: прогнать тестовые данные по слоям и получить протокол сверки с эталоном (срез поставки 1Б).
4. Наглядность: показать хранилище в браузере (схема потоков, карточки объектов, SQL) и пройти весь сценарий одной командой за 5–7 минут демонстрации.

## 2.3. Что прототип не делает

| Не входит | Почему | Что делает прототип |
|---|---|---|
| Прямое подключение к SAP (RFC, ODP, БД) | Нет доступа к BW; лицензионные вопросы | Работает только с CSV-выгрузками |
| Редактирование модели в UI, формулы в UI, анализ влияния | Поставка 1В | Схема и карточки только для просмотра |
| Разбор SQL обратно в модель | Поставка 1В, высокий технический риск | Вкладка SQL показывает код как текст |
| Развёртывание через ALTER, план изменений, версии модели с откатом | Поставка 1В | Пересоздание объектов в схемах прототипа |
| Модуль ручной загрузки с шаблонами и построчной проверкой, каскадный откат загрузок | Поставка 1Б целиком | Загрузка тестовых CSV через COPY с базовой проверкой |
| ABAP/AMDP-рутины, чтение атрибутов справочника в трансформации, BEx-запросы, иерархии, пересчёт валют, цепочки процессов, полномочия | Уровни 2–3 | Распознаёт и показывает в отчёте о сложности, код рутины показывает в карточке |
| CompositeProvider, InfoCube, классический DSO, MultiProvider | Вне потока «Продажи» | Распознаёт и показывает в отчёте о сложности |
| Сдвиг валют с другим числом знаков (TCURX, JPY) | Нет в демо-потоке | Валюты потока имеют 2 знака; ограничение записано в отчёте |
| Пользователи, роли, аутентификация | Локальное приложение одного пользователя | Имя пользователя берётся из учётной записи ОС для журналов |
| Работа без интернета, промышленные объёмы | Не нужно для защиты | Проверяется на демо-наборе; большой набор желателен (ФП-2.6) |

# 3. Характеристика объекта автоматизации

## 3.1. Исходный процесс

Сейчас при переносе хранилища SAP BW разработчики BW выгружают структуру таблиц, а разработчики целевой СУБД вручную пишут DDL для каждой таблицы, справочника, правила трансформации и витрины. Доказательства, что отчётность после переноса не изменилась, нет. Подробно процесс описан в process-analysis-bw-to-adb.docx.

## 3.2. Демонстрационный поток «Продажи»

Прототип строится вокруг одного потока (полный состав в приложении Б):

`ZSALES_FF` (плоский файл) → `TR_00` → `ZSD_A01` (ADSO standard с журналом изменений, позиции продаж) → `TR_01` → `ZSD_A02` (ADSO cumulative, продажи по клиенту и месяцу)

Справочники: `0SOLD_TO` (клиент, атрибут страна, тексты), `0MATERIAL` (материал, атрибут группа материалов, тексты).

Чтобы отчёт о сложности был содержательным, синтетический набор метаданных дополнительно содержит объекты вне потока: ADSO staging и direct update (для проверки генерации всех видов ADSO), трансформацию с ABAP-рутиной, CompositeProvider, BEx-запрос, иерархию, цепочку процессов, классический DSO и неактивный объект.

## 3.3. Слои в целевой СУБД

| Слой | Схема | Что лежит |
|---|---|---|
| Вход | `<prefix>_stg` | Входные таблицы DataSource и входящие таблицы ADSO |
| Справочники | `<prefix>_md` | Атрибуты и тексты признаков |
| Хранение | `<prefix>_dwh` | Активные данные и журналы изменений ADSO |
| Витрины | `<prefix>_mart` | ADSO верхнего уровня (здесь `ZSD_A02`) |
| Служебный | `<prefix>_meta` | Журнал загрузок, журнал развёртываний, результаты сверок |

Префикс задаётся в настройках проекта (по умолчанию `dbt`). Схемы прототипа всегда отдельные, чужие схемы приложение не трогает.

# 4. Требования к системе

## 4.1. Требования к системе в целом

### 4.1.1. Структура

Система состоит из ядра на Python (импорт, модель, анализ, генерация, развёртывание, сверка), двух интерфейсов поверх ядра (командная строка и веб-интерфейс) и целевой СУБД Greengage в Docker. Интерфейсы не содержат бизнес-логики: любое действие веб-интерфейса доступно командой и наоборот.

### 4.1.2. Режимы работы

1. Пошаговый: пользователь выполняет команды или нажимает кнопки по отдельности (импорт, отчёт, генерация, развёртывание, загрузка, прогон, сверка).
2. Сквозной демо-режим: команда `dbtransfer run-demo` выполняет весь сценарий на демо-наборе и печатает итог.
3. Без базы: импорт, отчёт, схема и генерация SQL работают без запущенного Greengage.

### 4.1.3. Надёжность

- Ошибка на любом шаге останавливает этот шаг, сообщает объект, шаг и причину и не оставляет базу в полуразвёрнутом состоянии: развёртывание выполняется в транзакции, прогон одной загрузки по всему потоку тоже выполняется одной транзакцией (ФП-7.3).
- Повторный запуск импорта, отчёта, генерации и развёртывания на тех же входных данных даёт тот же результат и не падает на уже созданных объектах. Загрузка и прогон намеренно не идемпотентны: каждая загрузка получает новый `load_id`, а повторная активация уже активированной загрузки запрещена (ФП-7.6), иначе суммы в cumulative ADSO удвоятся.
- Ошибка в одном CSV-файле метаданных не прерывает импорт остальных; в отчёте о проверке файлов перечислены все проблемы.

### 4.1.4. Безопасность

- Параметры подключения к базе хранятся в файле `.env` (в `.gitignore`), в репозиторий попадает только `.env.example`. Пароль не пишется в журналы и не показывается в интерфейсе.
- Приложение работает только со схемами с заданным префиксом.
- В демо-данных нет реальных персональных данных и коммерческой тайны.

### 4.1.5. Эргономика и язык

- Интерфейс, сообщения, отчёты и протоколы на русском языке; технические имена объектов BW и SQL остаются как есть.
- Каждое сообщение об ошибке содержит: что за объект или файл, какое поле или строка, что не так, что сделать. Пример: «Файл RSDIOBJ.csv, строка 14: неизвестный тип InfoObject «XYZ». Проверьте поле IOBJTP или удалите строку».

### 4.1.6. Расширяемость

- Чтение источника оформлено адаптером (`importers/bw_csv`), генерация SQL оформлена диалектом цели (`generator/dialects/greenplum6`). Добавление другого источника или цели не требует правки модели и анализа.
- Соответствие таблиц и колонок выгрузок BW полям модели задано в конфигурационном файле `bw_tables.yaml`, а не в коде, чтобы реальные выгрузки с другим набором полей подключались правкой конфигурации.
- Правила перевода типов, хранения и именования заданы в `type_rules.yaml` и `naming.yaml`.

## 4.3. Требования к данным

### 4.3.1. Входные данные: выгрузки метаданных BW

- Формат: CSV, одна таблица BW на файл, имя файла равно имени таблицы (`RSDIOBJ.csv`), первая строка — технические имена полей.
- Состав таблиц и используемых полей — приложение А. Набор полей для реальной BW является гипотезой и уточняется по первой настоящей выгрузке; расхождения закрываются правкой `bw_tables.yaml`.
- Демо-набор лежит в `demo/bw_export/` и сделан по документации и общеизвестной структуре таблиц BW/4HANA. Он должен воспроизводить типичные особенности выгрузок SE16: разделитель `;`, кодировку Windows-1251 хотя бы в одном файле, десятичную запятую, пустые даты `00000000`.

### 4.3.2. Модель метаданных

Модель описывается классами pydantic и сериализуется в JSON. Минимальный состав:

| Класс | Основные свойства |
|---|---|
| `Project` | версия формата модели (`schema_version`), имя, версия BW, префикс схем, список объектов, время импорта, хеш модели. Модель с неизвестной `schema_version` не открывается и даёт понятную ошибку |
| `InfoObject` | имя, вид (признак, показатель, время, единица), тип и длина BW, тип ADB, конвертация (ALPHA), атрибуты, наличие текстов; для показателя — тип (сумма, количество, число), единица или валюта, агрегация |
| `Adso` | имя, вид (staging, standard, cumulative, direct update), поля, ключ, параметры ADB (ключ распределения, хранение по таблицам), слой |
| `Field` | техническое имя, InfoObject, тип BW, тип ADB, ключевое, допускает NULL, комментарий |
| `DataSource` | имя, исходная система, вид (flat file, прочее), поля |
| `Transformation` | id, источник, цель, правила полей, рутины (вид, код), уровень |
| `Rule` | поле цели, вид (прямое, константа, формула, время, чтение атрибута, рутина), поля источника, параметр |
| `Dtp` | id, источник, цель, режим (полная, дельта), фильтр |
| `OtherObject` | тип (CompositeProvider, запрос, иерархия, цепочка, InfoCube, DSO и т. п.), имя, связи, уровень, причина |
| `Issue` | серьёзность, файл, строка, объект, сообщение |

Уровни автоматизации в прототипе:

| Уровень | Объекты |
|---|---|
| 1 | InfoObject; ADSO всех четырёх видов; Flat File DataSource; трансформация, все правила которой прямые, константы, формулы из словаря или преобразования времени; DTP полная или дельта |
| 2 | Трансформация с чтением атрибута справочника или AMDP-рутиной; CompositeProvider; классический DSO; InfoCube; DataSource не flat file |
| 3 | Трансформация с ABAP-рутиной; BEx-запрос; иерархия; цепочка процессов; объекты, которые не удалось разобрать |

Отличие от анализа процесса: там CompositeProvider, DSO и InfoCube отнесены к уровню 1. В прототипе они уровень 2, потому что не генерируются; это сознательное сужение объёма.

### 4.3.3. Правила перевода типов

Хранятся в `type_rules.yaml`, значения по умолчанию:

| Тип BW / ABAP | Тип Greengage | Правило |
|---|---|---|
| CHAR(n) | varchar(n) | Значение как есть; ALPHA сохраняется в модели как правило отображения. Данные ожидаются во внутреннем формате BW (числовые значения с ведущими нулями: `0000000101`); ALPHA-преобразование при загрузке не выполняется, признаки с ALPHA перечисляются в отчёте о сложности |
| NUMC(n) | varchar(n) | Никогда не число: теряются ведущие нули |
| DATS | date | Неключевое поле: `00000000` и пусто → NULL. Ключевое поле: NOT NULL, `00000000` и пусто → `0001-01-01` (значение-заглушка, настраивается) |
| TIMS | time | `000000` → `00:00:00` |
| CURR(p,d) + CUKY | numeric(p,d) + varchar(5) | Сдвиг по TCURX не выполняется (раздел 2.3) |
| QUAN(p,d) + UNIT | numeric(p,d) + varchar(3) | — |
| DEC(p,d) | numeric(p,d) | — |
| INT1, INT2, INT4 | smallint, smallint, integer | — |
| INT8 | bigint | — |
| FLTP | double precision | — |
| LANG | char(1) | — |
| CUKY, UNIT | varchar(5), varchar(3) | Как самостоятельные поля |
| STRING, SSTRING | text | — |
| Прочие (RAW, ACCP и т. п.) | text | С предупреждением в отчёте о проверке |

Ключевые поля NUMC и CHAR тоже NOT NULL: пустое значение хранится как пустая строка или начальное значение NUMC (`000000`), как в BW. Это важно для ключа `ZSD_A02`, где `0CALMONTH` вычисляется из даты.

### 4.3.4. Структура целевых таблиц ADSO

| Вид ADSO | Таблицы | Хранение по умолчанию | Ключ |
|---|---|---|---|
| staging | `stg.<имя>_inbound` | AO колоночная zstd | Нет PK |
| standard | `stg.<имя>_inbound`, `dwh.<имя>_active`, `dwh.<имя>_changelog` | inbound и changelog — AO колоночные; active — heap | PK только на active |
| cumulative | `stg.<имя>_inbound`, `<слой>.<имя>_active` | inbound — AO; active — heap | PK на active по всем признакам |
| direct update | `<слой>.<имя>_active` | heap | PK по ключу |

Служебные колонки: во входящей таблице `load_id bigint, record_no bigint, recordmode char(1)`; в журнале изменений `load_id bigint, record_no bigint, recordmode char(1)`. Значения `recordmode` в журнале: `N` новая запись, `X` before image (старые значения, показатели со знаком минус), пусто (`' '`) after image (новые значения). Ключ распределения всегда входит в PRIMARY KEY (ограничение Greenplum).

Особенности Greengage 6 (основа PostgreSQL 9.4), которые учитывает генератор: нет `CREATE PROCEDURE` и `CALL` (только функции), нет `INSERT … ON CONFLICT`, нет `GENERATED`/`IDENTITY` (номера загрузок — через последовательность); у append-optimized таблиц нет PRIMARY KEY и UNIQUE.

### 4.3.5. Семантика загрузки и активации

Правила ниже одинаково реализуют сгенерированный SQL и скрипт эталона `make_demo_data.py`; пример по ним посчитан вручную в приложении Д.

1. **Номер загрузки.** `load_id` присваивается при загрузке плоского файла и проходит через весь поток без изменений: входная таблица DataSource, входящая таблица, журнал изменений `ZSD_A01` и входящая таблица `ZSD_A02` получают тот же `load_id`.
2. **Режимы DTP.** Дельта: читаются записи источника с `load_id`, который этот DTP ещё не обрабатывал (для DataSource — входная таблица, для ADSO standard — журнал изменений). Полная: читаются все записи источника (все загрузки входной таблицы или активные данные ADSO) и пишутся в цель одной новой загрузкой; в демо-потоке полная загрузка не используется и проверяется только golden-тестом SQL. Оба DTP демо-потока — дельта.
3. **Дубли ключа внутри загрузки (standard).** Из записей одной загрузки с одинаковым ключом берётся одна, с наибольшим `record_no` (последняя в файле). В журнал изменений по такому ключу пишется одна пара образов.
4. **Активация standard.** Для каждого ключа загрузки: если ключа нет в активных данных — вставка в активные данные и запись `N` в журнал; если есть — запись `X` (старые значения, показатели с минусом) и `' '` (новые значения) в журнал, затем замена строки в активных данных. Пара `X`/`' '` пишется и тогда, когда значения не изменились (как в BW); суммарный вклад такой пары равен нулю. Удаления (`D`) и обратные записи (`R`) в прототипе не поддерживаются: строка входного файла с таким `recordmode` — ошибка загрузки.
5. **Активация cumulative.** Записи загрузки группируются по ключу, показатели суммируются и прибавляются к активным данным; отсутствующий ключ вставляется. Строки, у которых все показатели стали нулевыми, **остаются** в активных данных. В BW поведение зависит от настроек объекта; на реальной системе решение сверяется отдельно.
6. **Порядок.** Загрузки одного объекта активируются строго по возрастанию `load_id` (ФП-7.7); повторная активация запрещена (ФП-7.6).

Методика сверки (закрывает замечание ревью о тестовом срезе и вопрос В-7 для прототипа):

1. На вход подаются данные уровня DataSource (плоский файл), а не активные данные; срез — все загрузки по порядку, потому что активные данные ADSO с перезаписью являются итогом всей истории загрузок.
2. Эталон — активные данные проверяемого ADSO на том же срезе.
3. Для синтетического набора эталон вычисляется отдельным скриптом `demo/tools/make_demo_data.py` на pandas по правилам 4.3.5, независимо от генерируемого SQL. Так эталон не повторяет возможные ошибки генератора. Сам скрипт и SQL дополнительно проверяются на примере из приложения Д, посчитанном вручную: так ловится общая для обоих ошибка в понимании семантики BW.
4. Чтение атрибутов справочника в потоке не используется, поэтому ловушка «атрибут на момент загрузки против текущего» в прототипе не возникает; для реальной BW она описана в рисках.
5. Значения ключей во всех демо-файлах во внутреннем формате BW (с ведущими нулями для ALPHA), справочники и факты соединяются без преобразований.
6. Критерий успеха: 100% строк «совпало» на корректном эталоне; на испорченном эталоне найдены ровно 3 расхождения; пример из приложения Д совпал и для скрипта эталона, и для SQL.

Схема строится как граф DOT и выводится через `st.graphviz_chart` (не требует установки Graphviz в систему). Если выяснится, что этого недостаточно для читаемости, допускается pyvis (новая зависимость по правилу 4.5.3).

Требования к отзывчивости на демо-наборе: переключение вкладок и открытие карточки не дольше 2 секунд.

# 8. Допущения, ограничения и риски

## 8.1. Допущения

- Реальной системы BW нет; используется синтетический набор BW/4HANA. Классические объекты BW 7.5 только распознаются.
- Набор полей таблиц метаданных BW является гипотезой; первая реальная выгрузка потребует правки `bw_tables.yaml` и, возможно, импорта.
- Приложение работает у одного пользователя локально.

## 8.2. Риски

| Риск | Влияние | Как снижаем |
|---|---|---|
| Образ Greengage не запускается на конкретном компьютере (Windows, Apple Silicon) | Высокое | Проверка на шаге 1; запасной Cloudberry; часть тестов на обычном PostgreSQL |
| Синтетические выгрузки не похожи на реальные, на защите спросят | Среднее | Явно сказать об этом; показать, что формат вынесен в конфигурацию; искать консультанта BW для обезличенной выгрузки |
| На реальной BW сверка не сойдётся из-за атрибутов справочника на момент загрузки, рутин, валют | Среднее (вне прототипа) | Описано в методике; выбор потока без рутин для первой реальной сверки |
| Таблицы правил трансформаций (`RSTRANRULE`, `RSTRANFIELD`, `RSTRANSTEP`) на реальной системе устроены иначе, чем в гипотезе приложения А | Высокое для lineage и генерации трансформаций | Формат вынесен в `bw_tables.yaml`; на первой реальной выгрузке первым проверяется именно разбор правил |
| На реальных данных значения с ALPHA приходят во внешнем формате (без ведущих нулей), справочники и факты не соединяются, сверка расходится | Среднее (вне прототипа) | Признаки с ALPHA перечислены в отчёте о сложности; преобразование ALPHA — кандидат в следующую версию |
| Схема потоков нечитаема на большом наборе | Низкое | Фильтры и поток от объекта; на демо-наборе 15–25 узлов |
| Объём не укладывается в 7 недель | Среднее | Сначала все «О» командной строки (шаги 1–4), интерфейс последним; «Ж» по остатку времени |

# Приложение В. Словарь функций формул

Формулы трансформаций, которые прототип переводит автоматически. Всё остальное — уровень 2 с пометкой «формула не поддерживается».

| Формула BW | SQL Greengage |
|---|---|
| `+ - * /` | `+ - * /` (деление через `NULLIF(b, 0)`) |
| `IF(усл; a; b)` | `CASE WHEN усл THEN a ELSE b END` |
| `= <> < > <= >=`, `AND`, `OR`, `NOT` | те же операторы |
| `CONCATENATE(a; b)` | `concat(a, b)` |
| `SUBSTRING(s; pos; len)` | `substr(s, pos + 1, len)` (в BW позиция с 0) |
| `STRLEN(s)` | `length(s)` |
| `TOUPPER(s)` | `upper(s)` |
| `ABS(x)` | `abs(x)` |
| `ROUND(x; n)` | `round(x, n)` |
| `IS_INITIAL(x)` | `(x IS NULL OR x = '' OR x = 0)` по типу поля |
| `DATE_YEAR(d)` | `coalesce(to_char(d, 'YYYY'), '0000')` |
| `DATE_MONTH(d)` | `coalesce(to_char(d, 'YYYYMM'), '000000')` |

Пустая дата в функциях даты даёт начальное значение, как в BW и в правиле преобразования времени `TR_01`; иначе результат в ключевом поле нарушит `NOT NULL`.

Синтаксис формул в синтетическом наборе фиксируется тестами; на реальной BW перечень сверяется с фактическими формулами.

# Приложение Д. Пример, посчитанный вручную
