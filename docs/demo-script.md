# Сценарий демонстрации (5–7 минут)

Сценарий для защиты прототипа DB-transfer. Курсивом — что говорить, обычным текстом — что делать. Время в скобках — ориентир от начала.

## Подготовка (до защиты, без зрителей)

1. Запустить Docker Desktop и базу: `docker compose up -d`. Через 1–3 минуты проверить: `uv run dbtransfer db check` показывает версию Greengage и пишет «Права на создание схем есть. Всё готово.».
2. Прогнать сценарий целиком один раз: `uv run dbtransfer run-demo`. Должно закончиться строкой «Демо прошло: цифры совпали с эталоном». Это заодно заполняет базу, чтобы на защите карточки и превью данных уже работали.
3. Запустить интерфейс: `uv run dbtransfer ui`, открыть `http://localhost:8501` в браузере, развернуть окно на весь экран, масштаб 90–100%.
4. Открыть DBeaver с подключением к базе `demo` (на случай вопросов «а где это в базе»).
5. Держать открытым второй терминал в папке проекта для запасного варианта (см. в конце).

Интернет на защите не нужен: образ Greengage уже скачан, интерфейс работает локально.

## 1. Постановка (0:00–0:40)

Вкладка «Импорт».

*Компании, которые уходят с SAP BW, переносят хранилище вручную: смотрят каждый объект в BW и пишут таблицы и загрузки заново. DB-transfer делает это по выгрузке метаданных: читает структуру хранилища, оценивает, сколько можно перенести автоматически, генерирует SQL для Arenadata DB, разворачивает его и проверяет, что цифры на выходе совпали с BW.*

*Вход — обычные выгрузки таблиц метаданных BW через транзакцию SE16, вот их список.* Раскрыть «Какие таблицы BW выгрузить и как (SE16)», показать список, свернуть.

## 2. Импорт (0:40–1:20)

Нажать «Импортировать» (папка `demo/bw_export`).

*Импорт читает 21 таблицу, проверяет колонки и ссылки между объектами и строит модель хранилища. Ошибки не роняют импорт, а попадают в отчёт с файлом, строкой и советом, что исправить.* Показать строку «Пропущены неактивные объекты».

*Наш демо-поток — продажи: плоский файл, два уровня ADSO, CompositeProvider и запрос. Плюс несколько объектов, которые прототип не переносит, чтобы показать, как они попадают в отчёт.*

## 3. Схема потоков и карточки (1:20–3:00)

Вкладка «Схема».

*Это схема потока данных, она строится из модели. Цвет рамки — уровень автоматизации: зелёный — переносится полностью автоматически, жёлтый — нужна проверка, красный — нужна ручная работа. Красное ребро — трансформация с ABAP-рутиной.*

В списке «Карточка» выбрать `ZSD_A02`.

*Карточка показывает, во что превратится объект в Arenadata DB: какие таблицы, как они хранятся, по какому ключу распределены, какие типы полей. Например, NUMC стал varchar, чтобы не потерять ведущие нули.*

Lineage: выбрать поле `0NETVAL_INV`, нажать «Откуда пришло».

*Самое полезное для аналитика — откуда пришло поле отчёта. Выручка в витрине пришла из ADSO нижнего уровня, а туда — по формуле «сумма минус скидка» из двух полей файла. Путь подсвечен на схеме оранжевым, рядом — где каждое поле лежит в Arenadata DB. Это же можно выгрузить в Excel.*

Нажать «Куда идёт» для того же поля. *В обратную сторону — до CompositeProvider и запроса: видно, какие отчёты затронет изменение поля.*

Нажать «Сбросить подсветку». В «Карточке» выбрать `TR: ZSD_A01 → ZSD_A03`.

*А вот трансформация с конечной рутиной ABAP. Автоматически её не перевести: генератор создаёт заготовку, а прогон через неё запрещён, пока человек не перепишет логику. Код рутины здесь же.*

## 4. Сложность (3:00–3:40)

Вкладка «Сложность».

*Итог для менеджера проекта: 26 объектов из 33 переносятся автоматически, это 79%. Остальное — ручная работа, оценка по нормам 28 часов. Отчёт скачивается в Excel с причинами по каждому объекту.*

## 5. SQL (3:40–4:10)

Вкладка «SQL». Выбрать файл `060_activation.sql`.

*Сгенерированный пакет: схемы по слоям, таблицы, функции активации и трансформаций. Это функция активации ADSO: она повторяет логику BW — новые значения перезаписывают старые, а в журнал изменений пишется пара строк «до» и «после». Пакет детерминированный: два запуска дают одинаковые файлы, его можно положить в git.*

## 6. Развёртывание, загрузка, прогон (4:10–5:30)

Вкладка «Развёртывание».

*Теперь проверим, что SQL рабочий. План показывает, что будет создано. Дальше — весь путь одной кнопкой: развернуть с пересозданием, загрузить справочники и две загрузки продаж, прогнать их по потоку и сверить.*

Нажать «Запустить демо целиком». Пока идёт (несколько секунд), сказать:

*Вторая загрузка специально содержит корректировки: изменение суммы, месяца, клиента, валюты и повторы без изменений. На них видно, правильно ли работает журнал изменений и пересчёт витрины.*

Показать итог и журнал загрузок: две загрузки со статусом «activated».

## 7. Сверка (5:30–6:30)

Вкладка «Сверка». Объект `ZSD_A02`, эталон `etalon_ZSD_A02.csv`, нажать «Сверить».

*Эталон — это то, что BW выдал бы по тем же данным. Сверяем каждую строку по ключу и каждый показатель: все 142 строки совпали, суммы по валютам и единицам совпадают.*

Выбрать эталон `etalon_ZSD_A02_broken.csv`, нажать «Сверить».

*А это эталон, в котором мы испортили три значения. Сверка находит ровно три расхождения, показывает ключ и разницу и автоматически сверяет нижний слой: он совпал, значит, ошибка на верхнем уровне. Протокол — в Excel и в служебной таблице базы.*

## 8. Итог (6:30–7:00)

*Итого: по выгрузке метаданных BW прототип оценил перенос, сгенерировал работающий SQL для Arenadata DB и доказал совпадение цифр с эталоном. Дальше — больше видов объектов и источников: Oracle, MS SQL, и целевые СУБД из семейства Greenplum и PostgreSQL.*

## Если что-то пошло не так

| Ситуация | Что делать |
|---|---|
| Интерфейс не открывается | В терминале `uv run dbtransfer ui --port 8502`, открыть `http://localhost:8502` |
| «Нет подключения» на вкладке «Развёртывание» | `docker compose ps`; если контейнер остановлен — `docker compose up -d` и подождать 1–3 минуты. Пока ждём — показывать вкладки «Схема», «Сложность», «SQL»: им база не нужна |
| Демо в интерфейсе упало | Показать то же в терминале: `uv run dbtransfer run-demo` — печатает итог с теми же цифрами |
| Схема мелкая на проекторе | Масштаб браузера 110–125% или кнопка полноэкранного просмотра в правом верхнем углу схемы |

## Частые вопросы

- **Откуда метаданные, если доступа к BW нет?** Прототип работает на синтетической выгрузке, собранной по документации BW/4HANA. Состав колонок вынесен в `dbtransfer/rules/bw_tables.yaml`, его можно поправить под реальную выгрузку без изменения кода.
- **Что с ABAP-рутинами?** Они определяются, оцениваются по трудоёмкости и показываются с кодом; генерируется заготовка, прогон через неё блокируется. Автоматический перевод ABAP — за рамками прототипа.
- **Почему Greengage, а не Arenadata DB?** Greengage — открытый форк Greenplum 6, на котором основан Arenadata DB; SQL для них одинаковый. Тесты CI проверяют пакет на настоящем Greengage.
- **Сколько времени занимает демо?** `run-demo` укладывается в секунды на демо-наборе; требование ТЗ — не дольше 2 минут.
